## 1. STARTUP & LIFECYCLE

- Entry point is a thin signal-context wrapper around cobra; `//go:generate` for i18n keys lives here — `main.go:12`, `main.go:19-22`
- Root command registers subcommands `testenv`, `upload`, `watch` (a **local-filesystem** watch CLI, unrelated to Telegram watch) — `cmd/root.go:21-24`, `cmd/watch/cmd.go:14-33`
- `cmd.Run` is the default cobra Run: parses boot flags, calls `boot.Init`, cleans cache only if no unfinished tasks, builds `app.New(...).Start()`, then blocks on `application.Done()` and calls `application.Stop()` — `cmd/run.go:21-67`
- Boot flags: `--config` (legacy TOML path/URL, "imported once"), `--data-dir` (default `./data`), `--db-path` (default `<data-dir>/saveany.db`), `--listen`, `--no-web`; env fallbacks `SAVEANY_DATA_DIR/DB_PATH/LISTEN` — `boot/flags.go:11-26`, `boot/flags.go:44-56`
- `boot.Init` order: mkdir data dir → `database.Init(ctx, dbPath)` → legacy import if `!settings.LegacyImported` → `database.MigrateMinioStorageType` → `settings.NewService` → mkdir temp dir → `EnsureAdmin` (web password) → log level → `i18n.Init` → `parsers.Configure` → `cache.Init` → proxy transport — `boot/boot.go:29-86`
- `app.Start` order: `bot.SetRestartHandler` → `database.MarkInterruptedTaskRecords` → `worker.Init` (helper-bot upload workers) → `core.Run` (task workers) → parser plugin load → `go handlers.ListenUserbotMediaEvents` (watch pump) → web server start → `go ApplyTelegram` (starts bot+userbot) → `go resume.Run` (restart recovery) — `app/app.go:60-116`
- Web server starts inside `app.Start` when `!NoWeb && cfg.Web.Enable`; token from `cfg.Web.APIToken` or freshly generated via `config.GenerateToken()` — `app/app.go:87-101`
- Graceful shutdown sequence: cancel ctx → wait `resumeDone` (5s) → `web.Stop` → `bot.Stop` → `user.Stop` → `worker.StopAll` → `core.Close` → `core.WaitWorkers(10s)` → `storage.CloseAll` → `database.Close` — `app/app.go:184-212`
- The binary **embeds** the web UI: `//go:embed all:dist` in `web/embed.go:5`. `web/dist/.gitkeep` is committed, so `go build ./...` compiles with an empty UI; a runnable-with-UI binary requires `pnpm --dir web/ui run build` first (Makefile `web` target touches `../dist/.gitkeep`) — `Makefile:10-11`
- Docker builds UI in a `node:26-alpine` stage and copies `--from=web /dist ./web/dist` before `CGO_ENABLED=0 go build`; runtime image adds `curl ffmpeg yt-dlp` — `Dockerfile:1-46`
- Full no-Docker build is `pnpm install/build` then `CGO_ENABLED=0 go build -trimpath -o saveany-bot .` — `Makefile:13-14`

## 2. SETTINGS / CONFIG SYSTEM

- Live config is an atomic snapshot: `var current atomic.Pointer[Config]`; `config.C()` returns a copy ("Callers must not mutate it"), `config.Set(cfg)` replaces it — `config/config.go:87-113`
- `Config` struct holds core knobs plus nested groups (Log, Aria2, Cache, Users, Temp, DB, Telegram, Storages, Parser, Hook, Ytdlp, Web, Metadata, Media); Storages are typed `storage.StorageConfig` interface values — `config/config.go:19-52`
- Persistence is SQLite key/value: `Setting{Key string PK, Value text, UpdatedAt}` — `database/model.go:53-57`; upsert via `clause.OnConflict` — `database/setting.go:23-32`
- Keys are group names (`core`, `log`, `db`, `telegram`, `aria2`, `cache`, `temp`, `ytdlp`, `parser`, `hook`, `web`, `metadata`, `media`) with JSON values, plus `auth` (bcrypt hash) and `meta.*` markers — `settings/settings.go:30-43`, `settings/settings.go:213-215`, `settings/settings.go:588-595`
- `settings.Load` builds a full `config.Config` from DB: applies each group JSON onto `config.Default(dataDir)`, skips `auth`/`meta.*`, then rebuilds `cfg.Users` from the `users` table (incl. `StorageFilterIDsJSON`/`StorageFilterMode`) and `cfg.Storages` from `storages` rows via `NewStorageConfigFromJSON` + `Validate()` (invalid rows are logged and skipped) — `settings/settings.go:205-307`
- Runtime change path: `Service.UpdateGroup(group, patch)` → merge JSON patch into current group (rejects unknown fields, skips `__MASKED__`) → `applyGroup` → `validateGroup` → `database.SetSetting` → `reloadConfigLocked` (Load → `config.Set` → `i18n.Init` → log level → `parsers.Configure`) → returns `restartRequired` field list — `settings/settings.go:413-491`
- `Service.Config()` is just `config.C()`; `Reload` = `ReloadConfig` + `storages.Reload` (storage instances rebuilt, old ones retired but kept alive for in-flight tasks) — `settings/settings.go:313-360`, `storage/load.go:154-202`
- CLI `--listen` is a non-persisted override applied on every reload via `SetListenOverride` — `settings/settings.go:317-330`
- **v0 import hook**: `boot.Init` calls `settings.LegacyImported(ctx)` then `settings.ImportLegacy(ctx, opts.ConfigPath, opts.DataDir)` — `boot/boot.go:36-39`
- Idempotency marker: settings key `meta.legacy_config_imported` (`legacyImportedKey`, value = RFC3339 timestamp) written **inside the same DB transaction** as the imported data — `settings/legacy.go:23`, `settings/legacy.go:203-207`
- `ImportLegacy` reads TOML from `--config`, `./config.toml`, `/etc/saveany/config.toml`, or http(s) URL; viper-unmarshals onto defaults; **drops v0 session files** (`db.session`, `telegram.userbot.session` are replaced by v1 paths with a warning); imports storages as `StorageRecord` rows (name-deduped), maps `storages` name lists to storage **IDs** for user filters, disables users not present in the TOML, and maps `api.host/port` + `api.token` into the `web` group — `settings/legacy.go:57-213`, `settings/legacy.go:228-249`
- **This transaction is the template for our v0-DB importer**: copy the shape (check marker → transaction → upsert rows → write marker); a parallel `meta.fork_db_imported` key + `ImportLegacyDB(ctx, oldDBPath, dataDir)` beside `settings/legacy.go` is the natural home. Reading the old viper-free DB directly (same schema as fork v0) avoids TOML round-tripping.

## 3. DATABASE LAYER

- GORM over SQLite with a **build-tag-swappable driver**: default `ncruces/go-sqlite3/gormlite` (WASM, pure Go, `!sqlite_glebarez`), alternative `glebarez/sqlite` (modernc, pure Go) under tag `sqlite_glebarez`; both selected through `database.GetDialect` — `database/driver.go:1-12`, `database/driver_glebarez.go:1-12`
- DSN normalizer wraps the path as `file:` URL with pragmas `foreign_keys(1)`, `journal_mode(WAL)`, `busy_timeout(5000)`; Windows drive paths get an extra leading slash (`file:///D:/...`) to avoid UNC mangling — `database/dsn.go:9-30`
- `database.Init` opens with gorm logger (Error level), `PrepareStmt: true`, chmods 0600, then runs `migrate` — `database/db.go:17-44`
- Migration is **versioned, not bare AutoMigrate**: `schema_migrations(version, applied_at)` table; `CurrentSchemaVersion = 1`; each entry `{version, up}` runs in a transaction; refuses DB newer than build — `database/migration.go:11-72`. Fork adds a **migration 2** entry: `up` does `tx.AutoMigrate(&fork tables...)` + `tx.Exec("ALTER TABLE ... ADD COLUMN ...")` guarded by column-existence checks; bump `CurrentSchemaVersion` to 2. AutoMigrate is idempotent, so re-runs are safe.
- Models (all embed `gorm.Model` = id/created_at/updated_at/deleted_at unless noted):
  - `User`: ChatID (uniqueIndex), Silent, DefaultStorageID, DefaultDirID, Dirs, ApplyRule, Rules, WatchChats, WatchNotify, FilenameStrategy, FilenameTemplate, ConflictStrategy, Enabled, StorageFilterIDsJSON (`column:storage_filter_ids`), StorageFilterMode (default blacklist) — `database/model.go:11-28`
  - **`WatchChat`: UserID + ChatID composite unique `idx_watch_user_chat`, `MessageFilter string`** (e.g. `msgre:foo`) — `database/model.go:30-35`. That is the *entire* row: no per-watch storage, dir, cursor, or enabled flag.
  - `Dir`: unique `idx_dir_user_storage_path` (UserID, StorageID, Path) — `database/model.go:37-42`
  - `Rule`: UserID, Type, Content, StorageID, DirPath — `database/model.go:44-51`
  - `Setting` — `database/model.go:53-57`; `StorageRecord` (table `storages`): Name unique (64), Type (32), Enable, ConfigJSON (`column:config`), ConfigVersion — `database/model.go:59-68`
  - `BotWorker` (helper upload bots), `TaskRecord` (TaskID unique, Type, Status indexed, StorageName, StorageID, Path, Source, Params JSON + ParamsVersion, timestamps), `TaskItemRecord` (table `task_items`, per-file outcome with SourceChatID/SourceMsgID), `WebSession`, `TaskItemMetadata` (table `task_item_metadata`) — `database/model.go:71-149`
- Watch CRUD: `user.WatchChat` appends to the association and `db.Save`s it; `UnwatchChat` uses `Unscoped().Delete`; `WatchingChat` counts; `GetWatchChatsByChatID` is the fan-out query used by the watch pump — `database/chat.go:7-42`
- Storage CRUD + ref counting: `StorageReferences` counts users/dirs/rules bound to an ID before delete — `database/storage_record.go:5-36`, `database/storage_record.go:74-103`
- Task records: `MarkInterruptedTaskRecords`, `HasUnfinishedTasks`, `ListQueuedTaskRecords`, `ReplaceTaskItems`, `ListFailedTaskItems` — `database/task_record.go:11-170`
- Upstream itself demonstrates the "additive migration" pattern twice at boot: `MigrateMinioStorageType` rewrites legacy `type=minio` rows to `type=s3` (normalizing endpoint scheme, dropping `use_ssl`) — `database/storage_record.go:40-70`, invoked at `boot/boot.go:41-43`

## 5. TASK SYSTEM

- `core.Executable` interface: `Type/Title/TaskID/Execute`; optional `DestinationInfo` (StorageName/Path) and `ParamSource` (JSON params for restart rebuild) — `core/core.go:44-60`
- Queue is a generic in-memory doubly-linked list with cond-var `Get`, `Add` dedupes by ID, `Done` cancels + removes; **no persistence of queue order** — `pkg/queue/queue.go:20-104`
- Workers: `core.Run` spawns `config.C().Workers` goroutines; each loop: emit `PhaseStart` → exec `hook.exec.task_before_start` → mark record running → `exe.Execute(taskCtx)` → collect `ItemResult`s → status resolution (Cancelled vs Queued-on-interrupt vs Failed vs Partial vs Completed, each with exec hooks) → persist items + metadata → final `UpdateTaskRecord` → emit `PhaseDone` → `qe.Done` — `core/core.go:64-192`
- Submission: `AddTask` → `AddTaskWithSource` creates the `TaskRecord` **before** enqueue (source = `bot`/`api`/`retry`), serializes `TaskParams`, attaches task sink; on enqueue failure deletes the record — `core/core.go:227-294`
- Restart recovery: `resume.Run` loops `ListQueuedTaskRecords` → `rebuild(record)` from persisted `Params` (per task type; TG file tasks refetch source messages by ID, skip items in `spec.Done`) → `core.EnqueueExisting`; `ErrNeedsClient` keeps the record queued and retries every 15s until a Telegram client is up — `core/resume/resume.go:47-107`, `core/resume/resume.go:109-243`, `core/resume/resume.go:246-344`
- Resumable download: `tdler.DownloadToCache` reuses a complete cache file as-is, else downloads to `cachePath + ".part"` tracked by `resumeBitmap` (partSize-aligned block bitset, JSON sidecar with source identity kind/id/accessHash, atomically rewritten) — `common/tdler/download_cache.go:23-88`, `common/tdler/resume.go:51-104`, `common/tdler/resume.go:334`
- Relay state: helper-bot relayed files persist `.relay` sidecar (relay chat/message IDs + source identity) so a crash can re-resolve the relay message — `client/relay/state.go:16-48`, `client/relay/download.go:33`
- **File-completion call sites (dedup interception points)**:
  - single-file task: after download, before upload the file is statted and the upload happens inside a retry loop calling `storage.SaveWithPath`/`SaveWithProgress` — `core/tasks/tfile/execute.go:49-90`; after successful upload: `core.MarkTaskElementDone` → `saveMetadataSidecar` → cache removal — `core/tasks/tfile/execute.go:97-103`. A dedup hook can wrap `t.Storage` here (hash the local cache file between lines 47 and 49, and short-circuit the upload if a duplicate is found, reporting `ItemStatusSkipped`).
  - batch/album task: downloads complete → `t.recordDownloadComplete` per item → `saveBatchItems` → `SaveBatchWithProgress`/`SaveBatch` → `MarkTaskElementDone` per element — `core/tasks/batchtfile/execute.go:218-233`, `core/tasks/batchtfile/execute.go:237-280`
  - the cleanest *systemic* interception is a `storage.Storage` decorator applied at instance construction (`storage.NewStorage`) or a `StorageProgressSaver`-aware wrapper, because **every** upload funnels through `storage.SaveWithPath` (`storage/storage.go:112-121`) / `SaveBatch`.
- Cancellation: `core.CancelTask` persists Cancelled status **before** cancelling the ctx so the worker can distinguish user-cancel from shutdown-requeue — `core/core.go:324-360`
- Events: `taskevent.Sink` injected via context; API progress and webhooks subscribe without touching task code — `pkg/taskevent/taskevent.go:24-80`

## 6. STORAGE ABSTRACTION

- Core interface: `Init(ctx, cfg) / Type() / Name() / Save(ctx, reader, path) / Exists(ctx, path)`; capability interfaces: `StorageCannotStream`, `StorageBatchSaver` (`SaveBatch`), `StorageBatchProgressSaver`, `StorageProgressSaver` (`SaveWithProgress`), `StorageListable`, `StorageTester`, `StorageSidecarWriter`, `StoragePathSaver`, `StorageReadable`, `StorageCloser` — `storage/storage.go:21-138`
- Helper dispatchers: `WriteMetadataSidecar`, `SaveWithPath` (returns backend-chosen path for conflict rename) — `storage/storage.go:79-121`
- Registry: `storageConstructors map[storenum.StorageType]StorageConstructor` — currently alist, local, webdav, s3, telegram, rclone; `NewStorage` instantiates + `Init`s — `storage/storage.go:142-165`
- Type enum is go-enum generated from a comment: `/* ENUM(local, webdav, alist, telegram, s3, rclone) */` — `pkg/enums/storage/storages.go:6-9`
- **MinIO is already answered upstream**: v1 dropped `minio` as a type and migrates old minio records to `s3` at boot (`database/storage_record.go:40-70`); S3 config is endpoint/access/secret/bucket/base_path/region/virtual_host — `config/storage/s3.go:9-43`. **Recommendation: do not port fork's MinIO storage type; use the built-in `s3` backend pointed at MinIO**, and keep a data-migration for any fork-era `minio` rows (upstream's migration only fires for `type=minio`, which fork DBs will have — so `MigrateMinioStorageType` already covers fork DBs for free).
- ID resolution: runtime instances are keyed by **name** (`storage.Storages map[string]Storage`) but identity is the DB ID: `GetStorageByID` → `config.GetStorageByID(id)` → name → instance; `GetStorageByUserIDAndID` enforces per-user access via `HasStorageID` — `storage/load.go:15-151`
- `storage.ID(st)` maps instance → DB ID for records — `storage/load.go:58-66`
- Telegram storage: `Save` → `save` picks helper bot (`uploadContext`) with primary-bot fallback; `SkipLarge` silently skips oversized files (`telegram.go:192-196`); split via `splitSize` (config `split_size_mb` capped at max upload), lossless video split (`SplitLargeVideo` + `createLosslessVideoParts`) else ZIP split; media typing via mimetype + MP4/ffprobe metadata, thumbnail extraction — `storage/telegram/telegram.go:139-359`
- Upload limits: `MaxUploadFileSize = 4000*512KB ≈ 2GB`, `PremiumMaxUploadFileSize = 8000*512KB ≈ 4GB` (premium only for non-bot clients), `MaxPhotoSize 10MB`, `MaxAlbumItems 10` — `storage/telegram/telegram.go:42-45`, `storage/telegram/telegram.go:362-367`, `pkg/consts/tglimit/tglimit.go:10-15`
- Album batching: `SaveBatch`/`SaveBatchWithProgress` plan media groups from `SourceGroupKey`/`MetadataGroupKey`, album-eligible = image (non-webp/gif) or video, cap 10 per album — `storage/telegram/telegram.go:549-660`
- **Forum topics: absent.** The only `ForumTopic` hit in the tree is metadata *detection* of incoming forum messages — `pkg/metadata/metadata.go:138`. No `message_thread_id` is ever set on sends. Fork's forum-topic routing must add a field to `TelegramStorageConfig` (e.g. `thread_id`) and thread it through `prepareMedia`/`saveMediaGroup` sender calls (`storage/telegram/telegram.go:441-547`, `storage/telegram/telegram.go:689+`).
- **Adding a new storage type — every registration point**: (1) enum comment `pkg/enums/storage/storages.go:7` + regenerate (`go-enum`); (2) constructor in `storageConstructors` `storage/storage.go:142-149`; (3) typed config struct + `Validate` in `config/storage/` and `case` in both `newStorageConfig` and `setBaseConfig` — `config/storage/factory.go:37-73`; (4) `ValidateJSON` works automatically once (3) exists — `config/storage/validate.go:14-31`; (5) web UI form fields `web/ui/src/storageFields.ts:24+` + i18n labels; (6) optional boot migration in `database/storage_record.go` if importing fork rows. Again: MinIO needs none of these — use `s3`.

## 7. WATCH FLOW v1 END-TO-END

- Source: **userbot only** (docs warn "requires UserBot") — userbot dispatcher handler `handleMediaMessage` accepts photo/document media, builds `tfile.TGFileMessage`, and pushes into a debounced channel (5s per chat+msg, album members coalesce only via the later group logic) — `client/user/watch.go:71-100`, `client/user/watch.go:27-68`
- Pump: `app.Start` launches `handlers.ListenUserbotMediaEvents(ctx, resolve)` which resolves bot ctx for notifications — `app/app.go:80-85`
- Pipeline per event (`client/bot/handlers/watch.go:321-459`): drop if `!mediafilter.Allowed` (watch.go:333) → `GetWatchChatsByChatID` (watch.go:339) → per watch row apply `MessageFilter` (`msgre:` regex on message text, watch.go:350-366) → load `User`, require `DefaultStorageID != 0` (watch.go:371) → storage = user's **default** storage (`GetStorageByUserIDAndID`, watch.go:375) → default dir path (watch.go:377-384) → filename strategy (message/template, watch.go:386-414) → if album + rule says NEW-FOR-ALBUM, collect via `watchMediaGroupMgr` timer then `processWatchMediaGroup` (watch.go:417-426, 461-566) → else rule match may override storage **by name** (`GetStorageByUserIDAndName`, watch.go:428-442) → `coretfile.NewTGFileTask` + `core.AddTask` (watch.go:444-455)
- `processWatchMediaGroup` groups files by `GroupedID`, names album folder from first file, creates one task per file into `dir/albumDir/` — `client/bot/handlers/watch.go:461-566`
- Bot-side `/watch`: bare command opens interactive menu (add/list/notify/sync buttons); `/watch <chat> [filter]` adds directly; filter grammar is `type:data` with **only `msgre` supported** (compile-checked at add time) — `client/bot/handlers/watch.go:38-111`, `watch.go:75-91`
- No catch-up on restart: grep for cursor/min_id/offset_id/last_message in `client/` + `database/` returns nothing; events are live-only from the userbot update stream, and the debounced channel is lost on shutdown. Fork's catch-up cursor would need a new `WatchChat` column (e.g. `LastMsgID`) plus a `messages.getHistory` sweep on userbot start.
- Notifications: per-user toggle `User.WatchNotify`; `newWatchNotifyProgress` wraps task progress — sends one message **per file** on first progress via `openWatchNotification` (lazily, never blocking the pump), then edits it through `tftask.ProgressTrack`; per-task bot ctx copies avoid concurrency on the shared context — `client/bot/handlers/watch_notify.go:27-120`
- `syncPeers` imports dialog list into peer cache, exposed as a watch-menu button — `client/bot/handlers/sync_peers.go:8`, `client/bot/handlers/watch.go:233-247`
- Fork watch extensions land here: extra filter types = extend the two `switch filterType` sites (watch.go:75-91 add-time, watch.go:350-366 match-time) + extend `WatchChat.MessageFilter` grammar (or add columns in migration 2); per-watch storage/dir = new `WatchChat` columns consulted at watch.go:375-384.

## 9. MEDIA FILTER

- Instance-wide allowlist: `config.C().Media.AllowedMediaTypes` (empty = allow all); `Allowed(media)` classifies via `mediatype.Classify` then checks `Allows(typ)`; types are image/video/audio/document ("photo" alias accepted) — `common/mediafilter/mediafilter.go:12-33`, `pkg/mediatype/mediatype.go:29-100`
- All call sites (6): bot media album handler, save flow media/text handlers, telegraph/shortcut message utils, and the watch pump — `client/bot/handlers/media_group.go:61`, `client/bot/handlers/save.go:145`, `client/bot/handlers/utils/shortcut/message.go:38,100,177`, `client/bot/handlers/watch.go:333`
- Injection assessment: it is a package-level function reading the global config, **not** context-aware — a per-user/per-watch layer cannot be dropped in without touching these 6 sites. Cleanest fork approach: keep `mediafilter.Allowed` as the instance gate, and add a `mediafilter.AllowedFor(ctx/user, media)` consulted at the two ingestion chokepoints that already know the user (`save.go:145` area via `handleSilentMode`-resolved user, and `watch.go:333→351` where the watch row is in hand). A context-carried override (`mediafilter.WithOverride(ctx, preds)`) also works because both chokepoints build contexts.

## 12. WATCH OUT — v1 CONSTRUCTS THAT WILL FIGHT THE PORT

- **Storage names still leak in the rule/watch path**: rules match to a storage *name* and watch resolves it via `GetStorageByUserIDAndName` — `client/bot/handlers/watch.go:428-442`, `watch.go:493-501`; `TaskRecord.StorageName` is stored alongside ID and `core.EnrichTaskRecord` resolves ID-from-name — `core/core.go:296-301`. Dedup/MinIO code must prefer IDs; renames will orphan name-based rule matches.
- **`resolveStorage` is name-fallback-first on resume** (ID tried, then name) — `core/resume/resume.go:336-356`; renaming a storage breaks in-flight resume.
- **Watch rows are minimal and rigid**: `WatchChat` has only UserID/ChatID/MessageFilter with a composite unique index (one row per user+chat — cannot watch the same chat twice with different filters); no enabled flag, no storage/dir/cursor — `database/model.go:30-35`. Fork's per-watch storage/filter/cursor needs migration 2 with new columns.
- **Single global media filter**: package function over `config.C().Media` with 6 hardcoded call sites; no per-user/per-watch layering (see §9).
- **Watch notify is one message per file**, lazily opened, edited in place; no batch/digest — `client/bot/handlers/watch_notify.go:27-120`. Fork's batch notify must replace `openWatchNotification`/`watchNotifyProgress` (it's a `var`, so swappable in tests — `watch_notify_test.go`).
- **Watch uses the user's default storage only**; per-watch storage selection doesn't exist (`watch.go:371-384`).
- **No catch-up cursor / replay**: live userbot events only; anything queued in-memory is lost on restart (`client/user/watch.go:27-68`, verified absent in `client/`+`database/`).
- **Forum topics nowhere**: only detection in metadata, no send-side `message_thread_id` (see §6); fork topic routing touches Telegram storage config + all sender call sites including media groups.
- **`cmd/watch` name collision**: upstream's `watch` subcommand is a local-dir uploader — `cmd/watch/cmd.go:14-33`; docs/tests referencing "watch" may mean either; don't reuse the command name.
- **Settings are group-JSON with strict validation**: `UpdateGroup` rejects unknown fields (`settings/settings.go:421-431`); fork settings must be added to `coreGroup`/`applyGroup`/`validateGroup`/`restartRequired` quartet, not ad-hoc keys.
- **Queue is in-memory**: restart recovery only covers tasks whose `Params` persisted; dedup state must be DB-backed, not memory — `pkg/queue/queue.go:20-104`, `core/resume/resume.go:47`.
- **Storages keyed by name in the runtime map** while DB identity is ID; duplicate names are a hard config error at load (`settings/settings.go:249-253`) and creation (`settings/settings.go:663-703`).
- **`SkipLarge` is silent-by-design** (returns nil success) — `storage/telegram/telegram.go:192-196`; fork's "resend/SkipLarge reporting" must hook item results, not error paths.
- **Floodwait handling is a fixed middleware stack** (`recovery → retry → floodwait.NewSimpleWaiter`) — `client/middleware/default.go:14-20`; fork's floodwait meter/stall watchdog should wrap/extend this stack plus `rpclimit` (`common/utils/rpclimit/rpclimit.go`) rather than adding a second waiter.
- **Windows path quirks are handled upstream** — dsn drive-letter slash `database/dsn.go:24-28` and `cmd.exe /C` hooks `core/hookutil.go:13-17`; keep them when porting Dockerfile.micro/pico (use `sqlite_glebarez` or default ncruces; both CGO-free).
